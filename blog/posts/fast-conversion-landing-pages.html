Building Fast, Conversion-Focused Landing Pages

Mobile-first layout, sticky CTAs, forms that don't fight people, Core Web Vitals and conversion tracking, with the code I actually use.

9 October 2026 · 6 min read

A landing page has one job: get the right person to take one action. Everything on it either helps with that or gets in the way. I build a lot of these, for clients' ad campaigns and inside funnel builders like GoHighLevel, and over time I've ended up with a checklist I go through every time.

This is that checklist, with the code I actually use. None of it is clever. It's the boring details that decide whether someone on a mid-range phone on mobile data fills in your form or gives up.

Start with the phone

On most landing pages I've worked on, the majority of visitors are on a phone. [ADD A REAL FIGURE FROM ONE OF YOUR PROJECTS' ANALYTICS, E.G. "ON [PROJECT], 8 IN 10 VISITORS WERE ON MOBILE"] So I design and write CSS for the small screen first, then add to it for larger screens: 

.hero {
  display: grid;
  gap: 1.5rem;
  padding: 2rem 1.25rem;
}

.hero h1 {
  font-size: clamp(2rem, 8vw, 3.5rem);
  line-height: 1.05;
}

@media (min-width: 900px) {
  .hero {
    grid-template-columns: 1.1fr 1fr;
    align-items: center;
    padding: 5rem 2rem;
  }
}

Writing it this way round means the phone layout is the default rather than an afterthought patched in with overrides. A few rules I hold myself to:

  • On a 390px-wide screen, the headline, a one-line benefit and the call to action are visible without scrolling.
  • Buttons and links are at least 44px tall. Thumbs are not mouse pointers.
  • Nothing important hides in a carousel. Almost nobody swipes to slide four.

Sticky CTAs that know when to step aside

A sticky button at the bottom of the screen is one of the most reliable conversion tools on mobile, because the next step is always one tap away. But it should get out of the way when the form itself is on screen. Two buttons for the same action just look broken. 

<a class="sticky-cta" href="#get-quote">Get a free quote</a>
.sticky-cta {
  position: fixed;
  inset: auto 1rem calc(1rem + env(safe-area-inset-bottom)) 1rem;
  padding: 1rem;
  text-align: center;
  font-weight: 700;
  color: #fff;
  background: #111;
  border-radius: 999px;
  transition: transform 0.25s ease, opacity 0.25s ease;
}

.sticky-cta[inert] {
  transform: translateY(150%);
  opacity: 0;
}

@media (min-width: 900px) {
  .sticky-cta { display: none; }
}
const cta = document.querySelector(".sticky-cta");
const form = document.querySelector("#get-quote");

// Hide the sticky button while the form is visible
new IntersectionObserver(([entry]) => {
  cta.inert = entry.isIntersecting;
}).observe(form);

Using inert instead of only hiding the button visually means keyboard and screen reader users can't land on an invisible button either. The env(safe-area-inset-bottom) keeps the button clear of the iPhone home bar; it only works if your viewport meta tag includes viewport-fit=cover.

Forms: where conversions are won or lost

Every extra field is a reason to leave. Before I build a form, I ask the client what they'll actually do with each answer. If the answer is "nothing yet", the field goes. [IF YOU'VE MEASURED THE EFFECT OF REMOVING FIELDS ON A REAL PROJECT, ADD THE BEFORE/AFTER HERE]

Then I sweat the details:

  • 16px inputs. iOS Safari zooms in on any input with text smaller than 16px when you tap it, and the page stays zoomed. It's jarring, and the fix is one line of CSS.
  • The right keyboard. type="email", type="tel" and inputmode bring up the right keyboard; autocomplete lets the phone fill in the details for them.
  • Real labels. Placeholder text disappears the moment you start typing. Labels don't.
  • Errors at the right moment. Check a field when the person leaves it, and on submit. Not on every keystroke: nobody likes being told their email is invalid while they're still typing it.
  • Errors that say how to fix it. "Invalid input" is useless. "That doesn't look like a phone number. Try 0712 345 678" is helpful.
<form id="get-quote" novalidate>
  <label for="phone">Phone number</label>
  <input id="phone" name="phone" type="tel" inputmode="tel" autocomplete="tel"
         pattern="[0-9+ ]{9,15}" required aria-describedby="phone-error">
  <p id="phone-error" class="field-error" hidden></p>

  <button type="submit">Get my quote</button>
</form>
input, select, textarea {
  font-size: 16px; /* anything smaller and iOS Safari zooms in on focus */
}

input[aria-invalid="true"] { border-color: #b42318; }
.field-error { color: #b42318; font-size: 0.875rem; margin-top: 0.25rem; }
const form = document.querySelector("#get-quote");

const messages = {
  valueMissing: "Please add your phone number so we can call you back.",
  patternMismatch: "That doesn't look like a phone number. Try 0712 345 678.",
};

function check(input) {
  const error = document.getElementById(`${input.id}-error`);
  const problem = Object.keys(messages).find((key) => input.validity[key]);

  input.setAttribute("aria-invalid", String(Boolean(problem)));
  error.textContent = problem ? messages[problem] : "";
  error.hidden = !problem;
  return !problem;
}

form.addEventListener("focusout", (event) => {
  if (event.target.matches("input")) check(event.target);
});

form.addEventListener("submit", (event) => {
  const inputs = [...form.querySelectorAll("input")];
  const results = inputs.map(check); // check every field, so every error shows
  const firstInvalid = inputs[results.indexOf(false)];

  if (firstInvalid) {
    event.preventDefault();
    firstInvalid.focus();
  }
});

novalidate turns off the browser's own error bubbles (which look different in every browser) but keeps the validity checks, so the JavaScript only decides how errors are shown, not what counts as valid. aria-describedby ties each message to its field, so screen readers read the error out when the field is focused. In a real form, each field gets its own messages.

And once someone submits, tell them clearly what happens next: "Thanks, we'll call you within one working day" beats a generic "Success!".

Speed is a conversion feature

Google's Core Web Vitals are a useful scorecard. A page is "good" when, for at least 75% of visits, the largest piece of content appears within 2.5 seconds (LCP), the page responds to taps within 200 milliseconds (INP), and the layout doesn't jump around (CLS under 0.1).

On landing pages, images are usually the biggest win:

<!-- The hero image is usually the LCP element: load it early, never lazily -->
<img src="/img/hero-800.webp"
     srcset="/img/hero-480.webp 480w, /img/hero-800.webp 800w, /img/hero-1200.webp 1200w"
     sizes="(min-width: 900px) 50vw, 100vw"
     width="1200" height="800"
     alt="Technician installing solar panels on a roof"
     fetchpriority="high">

<!-- Everything below the fold can wait until it's needed -->
<img src="/img/testimonial.webp" width="600" height="400"
     alt="Shop owner standing at the counter" loading="lazy" decoding="async">
  • Sized for the screen. srcset and sizes let a phone download a 480px image instead of a 2,000px one.
  • Modern formats. WebP or AVIF are usually far smaller than JPEG at the same quality.
  • Width and height set. The browser reserves space before the image loads, so text doesn't jump. That's most of CLS solved.
  • Lazy loading, but not for the hero. loading="lazy" on the LCP image is one of the most common performance mistakes I see.

The other big one is third-party scripts. Chat widgets, heatmaps and several tracking pixels can easily weigh more than the page itself, and they're the usual reason a page feels slow to respond to taps. I audit them on every project and load anything non-essential after the page is interactive.

Then I measure with PageSpeed Insights, which shows real-user data when a site has enough traffic, and on a real mid-range Android phone on mobile data, because that's how a lot of people in Kenya will actually see the page. [YOUR BEFORE/AFTER LIGHTHOUSE OR LCP NUMBERS FROM A REAL PROJECT]

Track the conversion, not the click

None of this matters if you can't tell whether it worked. The conversion is a successful form submission, not a click on the submit button, so I send the event only after the server says yes: 

async function submitLead(form) {
  const response = await fetch(form.action, { method: "POST", body: new FormData(form) });
  if (!response.ok) throw new Error(`Lead form failed: ${response.status}`);

  // GA4's recommended event for leads. Mark it as a key event in GA4.
  gtag("event", "generate_lead", { form_id: form.id });
}

I also copy the UTM parameters from the URL into hidden form fields, so the CRM knows which ad or campaign each lead came from, long after analytics has moved on: 

const params = new URLSearchParams(window.location.search);

for (const key of ["utm_source", "utm_medium", "utm_campaign"]) {
  const field = form.querySelector(`input[name="${key}"]`);
  if (field && params.has(key)) field.value = params.get(key);
}

With that in place, you can look at the real funnel: page views, people who started the form, people who finished it. A big drop between "started" and "finished" points straight at the form, and that's usually where the next improvement is.

The checklist

  1. Phone layout first; headline, benefit and CTA visible without scrolling.
  2. A sticky CTA on mobile that hides when the form is on screen.
  3. Fewer fields, 16px inputs, real labels, helpful errors at the right time.
  4. Right-sized, modern images with width and height; lazy-load everything except the hero.
  5. Audit third-party scripts.
  6. Track successful submissions and keep the UTM parameters.

It isn't glamorous work. But a page that loads fast and is easy to fill in on a cheap phone will beat a beautiful slow one almost every time.
