Automating the Boring Stuff with Zapier and Make

When I pick Zapier, when I pick Make, how I handle errors and duplicates, what it costs as volume grows, and when I write code instead.

25 September 2026 · 7 min read

A lot of my automation work starts the same way. Someone tells me about a task they do every day and quietly hate: copying leads from a form into a spreadsheet, pasting the same welcome email, checking an inbox to see if anything new came in. [ONE REAL EXAMPLE OF A TASK A CLIENT ASKED YOU TO AUTOMATE]

None of these jobs is hard. They're just boring, and boring work is where mistakes creep in, like the lead that never got a reply because it came in on a Friday evening. This post is how I think about automating that kind of work with Zapier and Make: which tool I reach for, what a real workflow looks like, how I stop it from breaking quietly, what it costs as it grows, and the point where I put the no-code tools down and write code instead.

Zapier or Make?

Both tools do the same basic thing: when something happens in one app, do something in another. The difference is the shape of the thing you build.

Zapier is a list. A trigger at the top, then steps that run one after another. You can branch with Paths and stop early with Filters, but a Zap reads top to bottom like a recipe. Its app directory is enormous, and a non-technical person can open a Zap and understand it. That matters more than developers like to admit. If I hand a client a Zap, the person who looks after it next year probably isn't a developer.

Make is a canvas. You connect modules on a visual board, split the flow with routers, loop over lists with iterators and gather results back with aggregators. The feature I love most is that every run is inspectable: click any module and you see exactly what went in and what came out. When the logic is genuinely branchy, or you're handling lists (an order with twelve line items, say), Make is far more comfortable.

My rough rule:

  • Zapier when the flow is mostly a straight line, the client will maintain it, and the apps involved have solid Zapier integrations.
  • Make when there's real branching, looping over lists, a lot of reshaping data, or enough volume that per-step pricing starts to hurt.
  • Neither when the automation has quietly turned into software. More on that at the end.

A real-world workflow: lead form to follow-up

The workflow I've built most often, in different forms for different businesses, looks like this:

  1. Someone fills in a form on a landing page.
  2. They're created (or updated) as a contact in the CRM.
  3. The sales team gets a notification in Slack or, very often here in Kenya, on WhatsApp, because that's where sales teams actually live.
  4. The lead gets a follow-up email straight away, so they hear back while they're still interested.

In Zapier, that's a trigger, a clean-up step, a "find or create" step in the CRM, a notification step and an email step. In Make it's a webhook, a CRM search, a router that creates or updates the contact, then the notifications.

The cleaning step is the one people skip, and it's the one that saves you later. Phone numbers are the classic problem. Kenyan numbers arrive as 0712 345 678, 254712345678, +254 712 345678 or just 712345678, and to a CRM those are four different people. I normalise them with a small Code by Zapier step (the same logic works in Make's tools or a custom function): 

// Code by Zapier (JavaScript). Map the form's phone field to inputData.phone.
const raw = (inputData.phone || "").replace(/[^\d+]/g, "");

let phone = raw;
if (/^0[17]\d{8}$/.test(raw)) phone = "+254" + raw.slice(1); // 0712345678
else if (/^254[17]\d{8}$/.test(raw)) phone = "+" + raw; // 254712345678
else if (/^[17]\d{8}$/.test(raw)) phone = "+254" + raw; // 712345678

return {
  phone,
  valid: /^\+254[17]\d{8}$/.test(phone),
  email: (inputData.email || "").trim().toLowerCase(),
};

Two things to know about WhatsApp before you promise it to a client. Sending messages from a business number goes through the WhatsApp Business Platform (directly through Meta, or a provider like Twilio), and messages you start, rather than replies within 24 hours of the person messaging you, have to use a pre-approved template. Get the template approved before launch day, not on it.

For the follow-up itself, I keep it to one immediate email in the automation. It's tempting to build a whole sequence with Zapier's Delay steps, but a delayed Zap doesn't know the lead replied yesterday. Email sequences belong in the CRM or email tool, which can stop the sequence the moment someone answers.

Errors and duplicates: the part nobody demos

An automation that fails loudly is fine. The one that fails quietly is the one that costs money, because nobody notices until a customer asks why no one called them back.

Errors

In Zapier, I turn on Autoreplay where the plan allows it, so steps that fail because an app was briefly down get retried automatically. Then I make sure errors go somewhere a human actually looks. Email alerts get ignored, so I usually send them to a dedicated Slack channel.

In Make, every module can have an error handler, and choosing the right one is most of the work. For calls to APIs that sometimes time out or rate-limit, I use Break with incomplete executions turned on, so the run is saved and retried rather than lost. For optional steps (adding a tag, say) I use Ignore or Resume with a fallback value, so one small failure doesn't stop the lead from reaching sales.

The useful mental split: temporary failures (an API is down) should retry on their own; bad data (no email, a nonsense phone number) should stop and tell a person, because retrying won't fix it.

Duplicates

Duplicates come from everywhere. People double-click submit buttons. Many webhook senders retry if you don't respond quickly, so the same event arrives twice. A lead fills in the form, gets distracted, and fills it in again next week.

  • Find before you create. Always search the CRM by email or phone first and update the existing contact if there is one. This is exactly why the cleaning step matters: you can only match people reliably once their details are in a single format.
  • Use an idempotency key for events that don't have a natural ID. Combine the email, the form and the date into a key, store it (Storage by Zapier or a Make data store), and skip the run if you've seen that key before.
  • Deduplicate before notifying. A duplicate CRM record is untidy. Two salespeople calling the same lead ten minutes apart is embarrassing.

What it costs as volume grows

Prices change often, so check the current pricing pages, but the way the two tools count usage is worth understanding because it decides how a workflow should be built.

Zapier counts tasks: every action step that runs successfully. The trigger doesn't count, and neither do Filter and Paths steps. Make counts operations: every module that runs, including the trigger. A scheduled trigger that checks for new data can use operations even when there's nothing new, so I prefer instant webhook triggers wherever the app supports them.

The back-of-the-envelope maths is simple. Forty leads a day is about 1,200 runs a month. If each run has five billable steps, that's 6,000 tasks or operations a month, before any retries. [IF YOU HAVE REAL NUMBERS FROM A CLIENT PROJECT, ADD THEM HERE]

A few habits keep that number down:

  • Put filters as early as possible, so runs you don't care about stop before the paid steps.
  • Combine several small formatting steps into one code step.
  • Batch things that don't need to be instant. One hourly summary in Slack is cheaper, and frankly more readable, than a message per event. (New leads are the exception: those should be instant.)

When I switch to code

No-code tools are brilliant until the automation has quietly become software. The signs I look for:

  • The Zap has more code steps than app steps.
  • The monthly bill is more than a small server or serverless function would cost to run the same logic.
  • The workflow is now business-critical and needs version control, tests and code review.
  • The branching has become so tangled that nobody can follow the canvas any more.
  • You need tight control over retries, rate limits or response times.

When that happens, I usually don't throw everything away. I move the complicated part into a small function and let the no-code tool keep doing the simple glue. A serverless function on Netlify, for example, can receive the form submission directly: 

// netlify/functions/lead.js
export default async (request) => {
  const lead = await request.json();
  const email = String(lead.email || "").trim().toLowerCase();
  if (!email) return new Response("Missing email", { status: 400 });

  // upsertContact, notifySales and normalisePhone are your own small functions
  // (normalisePhone is the same logic as the Zapier step above)
  const contact = await upsertContact({ email, phone: normalisePhone(lead.phone) });
  if (contact.created) await notifySales(contact);

  return new Response("ok");
};

It's more work to set up and maintain than a Zap, which is why I don't start there. But it lives in Git, it can be tested, and its cost barely moves as volume grows.

The short version

Start with the tool the client can maintain. Clean your data before you do anything with it. Decide in advance what happens when a step fails, and make sure a duplicate can never cause a second phone call. Watch the usage numbers as the business grows, and when the automation starts behaving like software, give it the respect software gets.

If you have a boring, repetitive task that eats your week, that's usually the best place to start.
