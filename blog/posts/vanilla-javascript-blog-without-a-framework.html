Vanilla JavaScript Is Still Enough: Building a Blog Without a Framework

How this blog works: one posts.js file, cards rendered with plain JavaScript, a tag filter, and static pages that share properly.

16 October 2026 · 6 min read

When I decided to add a blog to my portfolio, the obvious move was to reach for a framework: Next.js, a headless CMS, maybe a Markdown pipeline. I've built with React and I like it. But my portfolio is plain HTML, CSS and JavaScript on Netlify, with no build step, and I wanted to keep it that way.

So the blog you're reading is vanilla JavaScript. There's no framework, no database and no build. This post walks through how it works, with the real code, and is honest about what I gave up to keep it this simple.

What I actually needed

Before choosing tools, I wrote down what the blog had to do:

  • A home page listing every post, newest first, with a filter by tag.
  • One page per post, with its own title and description, so links shared on LinkedIn and X show a proper preview card.
  • Previous and next links between posts.
  • Adding a post should take two steps: write the page, add it to a list.

The second point decided most of the design. Link previews are built by crawlers that read the raw HTML and don't run your JavaScript. If the title and Open Graph tags are injected by a script, LinkedIn never sees them. So every post has to be a real HTML file with its metadata written into the <head>. Once you accept that, everything else can be small.

One file lists every post

All the information the home page needs lives in blog/posts.js, a plain ES module that exports an array: 

export const posts = [
  {
    title: "Vanilla JavaScript Is Still Enough: Building a Blog Without a Framework",
    slug: "vanilla-javascript-blog-without-a-framework",
    date: "2026-10-16",
    description: "How this blog works: one posts.js file, cards rendered with plain JavaScript...",
    tags: ["JavaScript", "Frontend"],
    readingTime: 7,
    cover: "",
  },
  // ...one object per post
];

The slug is the file name, so slug doubles as the link to the post. Dates are plain YYYY-MM-DD strings, which has a nice side effect: they sort correctly as text, so "newest first" is one line: 

import { posts } from "./posts.js";

const newestFirst = [...posts].sort((a, b) => b.date.localeCompare(a.date));

I copy the array before sorting because sort() sorts in place, and I'd rather not change an imported module's data under the feet of anything else that uses it.

Rendering the cards

Each card is a template literal. I reused the card styles from my project grid, so the blog looks like the rest of the site without a single new layout rule: 

function postCard(post, index) {
  // ...cover image or line-drawing artwork goes in `media`

  return `
    <a class="project-card post-card" href="posts/${encodeURIComponent(post.slug)}.html">
      <div class="project-card__media">${media}</div>
      <div class="project-card__body">
        <h3>${escapeHTML(post.title)}</h3>
        <div class="post-card__meta">
          <time datetime="${post.date}">${formatDate(post.date)}</time>
          <span>${post.readingTime} min read</span>
        </div>
        <p>${escapeHTML(post.description)}</p>
      </div>
    </a>`;
}

Two small functions carry more weight than they look. The first is escapeHTML. I'm the only person writing posts.js, but the day I type a title with an ampersand or a < in it, I want it to show up as text, not break the page. Escaping anything that goes into innerHTML is a habit worth keeping even when you trust the data: 

function escapeHTML(value) {
  const entities = { "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;" };
  return String(value).replace(/[&<>"']/g, (char) => entities[char]);
}

The second is formatDate, which hides a classic JavaScript trap. new Date("2026-10-16") is parsed as midnight UTC, so for anyone west of London it displays as the 15th. Building the date from its parts creates it in the reader's own time zone instead: 

const dateFormat = new Intl.DateTimeFormat("en-GB", { day: "numeric", month: "long", year: "numeric" });

function formatDate(isoDate) {
  const [year, month, day] = isoDate.split("-").map(Number);
  return dateFormat.format(new Date(year, month - 1, day));
}

The tag filter

The filter buttons are built from the tags in the posts, so a new tag appears as soon as a post uses it. A Set removes the duplicates: 

const tags = [...new Set(newestFirst.flatMap((post) => post.tags))].sort();

Clicking a button re-renders the grid with the matching posts. There's one click listener on the container rather than one per button, and each button carries aria-pressed so screen readers know which filter is on: 

function show(tag) {
  const visible = tag === "All" ? newestFirst : newestFirst.filter((post) => post.tags.includes(tag));
  grid.innerHTML = visible.map(postCard).join("");

  filter.querySelectorAll(".chip").forEach((chip) => {
    chip.setAttribute("aria-pressed", String(chip.dataset.tag === tag));
  });

  // Keep the filter in the address bar so a filtered view can be shared
  const url = new URL(window.location.href);
  if (tag === "All") url.searchParams.delete("tag");
  else url.searchParams.set("tag", tag);
  history.replaceState(null, "", url);
}

filter.addEventListener("click", (event) => {
  const chip = event.target.closest(".chip");
  if (chip) show(chip.dataset.tag);
});

Putting the tag in the URL (/blog/?tag=Frontend) costs three lines and means a filtered view can be shared or bookmarked. It also means the tags on each post page are ordinary links back to the filtered list. A hidden aria-live message announces how many posts are showing after each click.

Previous and next, without editing old posts

If previous/next links were written into each HTML file, publishing a post would mean editing the one before it, which is exactly the kind of step I'd forget. Instead, each post page finds itself in posts.js and builds the links: 

function setUpPager(pager) {
  // The canonical URL is always the real address, even when testing locally
  const canonical = document.querySelector('link[rel="canonical"]')?.href ?? window.location.href;
  const slug = new URL(canonical).pathname.split("/").pop().replace(/\.html$/, "");
  const index = newestFirst.findIndex((post) => post.slug === slug);

  if (index === -1) {
    console.warn(`blog.js: no post in posts.js has the slug "${slug}".`);
    pager.remove();
    return;
  }

  const older = newestFirst[index + 1];
  const newer = newestFirst[index - 1];
  // ...render a link for each one that exists
}

I read the slug from the canonical URL rather than the address bar because Netlify can serve the same page with or without .html, and the canonical tag is already required for sharing anyway. If I forget to add a post to the list, the console tells me.

The small things that make it feel finished

  • Syntax highlighting comes from Prism, loaded from a CDN with defer, only on posts that contain code. The colours are my own CSS, using the same ink-and-bronze palette as the rest of the site.
  • Copy buttons are added to each code block by JavaScript, so the HTML stays a plain <pre><code> that works without them.
  • Dark mode reads the same localStorage key as the rest of the site, and a tiny inline script applies it before the page paints, so there's no white flash.
  • No three.js on the blog. My home page uses three.js and GSAP for the project slider. The blog has its own small script, so a reader opening a post doesn't download a 3D library they'll never see.

What I gave up

Keeping it this simple has real costs, and I'd rather be clear about them:

  • Repeated markup. Every post contains its own copy of the nav and footer. Change the nav, and you change it in every file. A static site generator would handle that with a layout.
  • Details written twice. A post's title, date and tags live in both posts.js and the post's <head>. They can drift apart if I'm careless.
  • The list needs JavaScript. The cards on the blog home page are rendered in the browser. Google runs JavaScript, and every post is also in the sitemap, but a crawler that doesn't run scripts sees an empty list.
  • HTML, not Markdown. I write posts in HTML. It's fine for me; it would be a barrier for a non-technical writer.

When I'd reach for something bigger

If this blog grew to dozens of posts, had several authors, or needed an RSS feed and Markdown, I'd move it to a static site generator like Eleventy or Astro. Not React, because the output would still be static pages; I'd just let a build step do the repetitive parts. Sharing layouts and generating metadata are exactly the problems those tools solve.

But for a portfolio with a handful of posts, the vanilla version has real advantages. There's nothing to install, nothing to upgrade and nothing to break when a dependency changes. It loads fast because there's almost nothing to load. And every line of it is code I can explain in an interview, which, for a portfolio, is kind of the point.

Frameworks are tools, not a requirement. Sometimes the best way to show you know JavaScript is to use less of everything else.
