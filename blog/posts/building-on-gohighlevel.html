What I've Learned Building on GoHighLevel

What GoHighLevel is genuinely good at, a full lead-to-booking workflow, custom code and webhooks, and the mistakes I see most.

2 October 2026 · 6 min read

I came to GoHighLevel as a frontend developer, and I'll be honest: I was a bit snobby about it. An all-in-one marketing platform with a drag-and-drop page builder didn't sound like "real" development. [HOW AND WHEN YOU FIRST STARTED WORKING WITH GHL]

[NUMBER] accounts later, I've changed my mind, not about drag-and-drop, but about what GoHighLevel is for. It isn't trying to replace developers. It's trying to replace the five or six separate tools a small business glues together to get from "someone filled in a form" to "someone booked a call". This post is what I've learned building on it: where it shines, a workflow I build all the time, how code fits in, and the mistakes I keep seeing.

What GoHighLevel is genuinely good at

The headline feature is that everything lives in one place and shares one contact record. That sounds small until you've debugged a lead that went missing somewhere between a form tool, a CRM, an email platform and a calendar app.

  • Funnels and websites. Pages, forms and surveys that write straight into the CRM, with no integration in between.
  • CRM and pipelines. Contacts, plus opportunities that move through stages you define (New lead, Contacted, Booked, Won). Those stages become triggers for automation.
  • Workflows. The automation builder: triggers, actions, waits, if/else branches and goals. Most of my time in GHL is spent here.
  • Calendars. Booking pages, round-robin assignment across a team, and sync with Google or Outlook calendars.
  • Conversations. One inbox for SMS, email, WhatsApp and social messages, so the team replies from one place.
  • Snapshots. You can package a whole account setup (funnels, workflows, pipelines) and load it into another account. For agencies, that's huge.

A workflow I build all the time

Here's the shape of a lead-to-booking system. The most important design decision is that it's several small workflows, one per event, not one giant workflow that tries to do everything. 

Workflow 1: New lead
  Trigger:  Form submitted (the landing page form)
  Action:   Create opportunity in "Sales" pipeline, stage "New lead"
  Action:   Notify the assigned team member
  Action:   SMS / WhatsApp: "Thanks {{contact.first_name}}, here's a link to book a call"
  Wait:     1 day
  Action:   Email with the booking link and an answer to the most common question
  Wait:     2 days
  Action:   Final SMS follow-up
  Goal:     Appointment booked  -> leave this workflow immediately

Workflow 2: Appointment booked
  Trigger:  Customer booked appointment
  Action:   Move opportunity to "Booked"
  Action:   Confirmation email + SMS
  Wait:     Until 1 day before the appointment -> reminder
  Wait:     Until 1 hour before the appointment -> reminder with the meeting link

Workflow 3: No-show
  Trigger:  Appointment status changed to "No show"
  Action:   Move opportunity to "No show"
  Action:   SMS with a link to rebook

A few details make this work in real life. The goal in Workflow 1 means a lead who books on day one never gets the day-three "just checking in" message. I also turn on stop on response in the workflow settings, so anyone who replies is handled by a human instead of a script. And the reminders use waits relative to the appointment time, not fixed delays, so they still land correctly when someone books three weeks out.

Splitting it up like this means that when something goes wrong, the execution logs point to one small workflow, and changing the reminder timing can't accidentally break lead capture.

Custom code and webhooks inside GHL

This is where being a developer really pays off. GHL gives you several ways out of the box, and each one solves a different problem:

  • Webhook actions send contact and event data out of GHL to any URL, for example to create an invoice in an accounting tool or log to a spreadsheet.
  • Custom webhooks (a premium action) let you set the method, headers, authentication and body yourself, so you can call almost any API directly from a workflow.
  • Inbound webhook triggers (also premium) let an outside system start a workflow, such as a payment provider confirming a payment, or a custom app creating a lead.
  • Custom code actions run JavaScript inside a workflow. Its outputs become values the next steps can use.

The custom code action is great for the little jobs the built-in actions don't quite cover, like splitting a "full name" field that a form collected as one box: 

// GHL "Custom code" action. Map the contact's full name into the action's inputs first.
// The editor shows the exact input variable name your account uses; inputData is the common one.
const fullName = (inputData.full_name || "").trim().replace(/\s+/g, " ");
const [firstName = "", ...rest] = fullName.split(" ");

return { first_name: firstName, last_name: rest.join(" ") };

For bigger jobs, I point a custom webhook at a small serverless function I control. The one thing I always add is a shared secret in a header, so random traffic can't trigger it: 

// netlify/functions/ghl-webhook.js: receives a GHL custom webhook
export default async (request) => {
  if (request.headers.get("x-webhook-secret") !== process.env.GHL_WEBHOOK_SECRET) {
    return new Response("Unauthorized", { status: 401 });
  }

  // The body is whatever you mapped in the webhook action, e.g. contact_id and email
  const payload = await request.json();
  await createInvoice(payload); // your own function

  return Response.json({ ok: true });
};

Inbound webhooks work the other way. You send GHL a sample payload once, map its fields to contact fields, and from then on any system that can make an HTTP request can start a workflow: 

{
  "email": "jane@example.com",
  "phone": "+254712345678",
  "source": "partner-referral",
  "utm_campaign": "october-launch"
}

Mistakes I see clients make

Most of the GHL accounts I'm asked to fix have the same handful of problems. None of them is exotic.

  • One giant workflow. Two hundred steps, a dozen branches, impossible to debug. Split by event.
  • Re-entry set the wrong way. Whether a contact can enter a workflow twice decides whether a returning lead gets the welcome sequence again or never hears from you. Choose on purpose.
  • No stop conditions. A lead replies "Yes, I'm interested!" and still gets "Just checking in!" three days later. Goals and stop-on-response fix this.
  • Duplicate contacts. Usually caused by phone numbers in mixed formats. Keep duplicate contacts turned off and send numbers in international format (+254...).
  • Tags as a junk drawer. Hundreds of tags nobody understands. Use pipeline stages and custom fields for where someone is, tags for groups, and agree on a naming convention.
  • Never testing on a real phone. SMS links that break, messages that split into three, and reminders sent at 3 a.m. because the account and calendar time zones don't match.
  • Ignoring consent. Opt-outs and DND settings matter, and WhatsApp messages you start need approved templates.

How developer skills make GHL work better

You can get a long way in GoHighLevel without writing a line of code. But the accounts that run smoothly tend to have someone who thinks like a developer behind them.

  • Thinking in states. I design pipelines the way I design UI state: every stage has a clear way in and a clear way out, and nothing can sit in two states at once.
  • Clean data. Normalising phone numbers and emails at the point of capture prevents most duplicate and delivery problems before they start.
  • Extending the edges. Webhooks plus a small function cover what GHL doesn't do natively, like a local payment confirmation that should mark an opportunity as won.
  • Frontend craft on funnels. Custom CSS and code on funnel pages, compressed images, and form inputs that don't zoom on iPhones. Fast pages convert better, in GHL or anywhere else.
  • Debugging like it's code. Reading execution logs, testing webhooks with sample payloads, changing one thing at a time, and writing down what each workflow is for.

GoHighLevel handles the parts every business needs. A developer makes it fit the parts that make that business different. That combination is the work I enjoy most right now.
